# ZAO110 — LINQ paging without OrderBy

**Severity:** Warning
**Category:** ZeroAlloc.ORM

## Trigger

Fires when a `[LinqQuery]` method that returns a list or a stream pages its rows with `Skip` or `Take`, and the chain has no `OrderBy` or `OrderByDescending`. Without an `ORDER BY`, PostgreSQL returns rows in whatever order its plan produces, so which rows a page holds can change from one call to the next, and paging can skip or repeat rows.

The query is still generated as written. ZAO110 does not fire for:

- the single-row shape, `Task<TRow?>`, and its implicit `LIMIT 1`;
- `Count()`, `LongCount()` and `Any()`, whose result does not depend on the order.

It is reported at the first `Skip` or `Take`.

## Fix

Order the rows before paging them, ending with a key that is unique, such as the primary key, so that rows with equal values keep a fixed order.

## Example

```csharp
// Fires ZAO110 — the page holds an arbitrary ten rows:
private static IQuery<TaskSummary> PageQuery(int skip) =>
    Sql.Table<TaskEntity>()
        .Skip(skip)
        .Take(10)
        .Select(t => new TaskSummary(t.Id, t.Title));
```

Fix:

```csharp
private static IQuery<TaskSummary> PageQuery(int skip) =>
    Sql.Table<TaskEntity>()
        .OrderBy(t => t.CreatedAt)
        .ThenBy(t => t.Id)
        .Skip(skip)
        .Take(10)
        .Select(t => new TaskSummary(t.Id, t.Title));
```

For deep pages, keyset paging with `Sql.Row` reads from the last row seen instead of skipping:

```csharp
private static IQuery<TaskSummary> NextPageQuery(DateTimeOffset afterAt, Guid afterId) =>
    Sql.Table<TaskEntity>()
        .Where(t => Sql.Row(t.CreatedAt, t.Id) > Sql.Row(afterAt, afterId))
        .OrderBy(t => t.CreatedAt)
        .ThenBy(t => t.Id)
        .Take(10)
        .Select(t => new TaskSummary(t.Id, t.Title));
```
