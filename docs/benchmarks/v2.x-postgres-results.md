# v2.x Postgres benchmark results

**Status:** Captured 2026-10-30 for [#351](https://github.com/ZeroAlloc-Net/ZeroAlloc.ORM/issues/351), on `main` at
`6b95bce` plus the per-dialect parameter names.

> Allocations are close but not exact; see below. Speed is shown as same-run ratios; absolute
> timings are not published.

ZA.ORM is a **relative-position** tool: compare the rows of one table, never numbers across tables
or machines.

## Environment

```
BenchmarkDotNet v0.15.8, Linux Debian GNU/Linux 13 (trixie)
Intel Core Ultra 7 255H 3.69GHz, 1 CPU, 12 logical and 12 physical cores
```

## Reproduction

```bash
# From repo root; Docker must be reachable.
dotnet run -c Release --project tests/ZeroAlloc.ORM.Benchmarks -- --anyCategories Postgres
```

## How to read the tables

- **Ratio** is each row's mean time divided by `HandWrittenAdoNet`'s in the same run.
- **Allocated** is bytes per operation from BenchmarkDotNet's GC counters.
- **Alloc Ratio** is each row's allocation divided by `HandWrittenAdoNet`'s.
- `HandWrittenAdoNet` is written against `NpgsqlConnection` itself. `HandWrittenAsyncDb` is the
  same code against `IAsyncDbConnection`, the AdoNet.Async substrate ZA.ORM's generated code runs
  on.
- Every hand-written row binds bare names such as `id`, which Npgsql need not trim. Earlier
  captures bound `@id`, which costs Npgsql a Substring per parameter, so their baselines were
  about 32 B per parameter heavier than this one's. ZA.ORM binds bare names on
  `[Dialect(SqlDialect.PostgreSql)]`, which every Postgres benchmark repository declares.

Allocations are not whole numbers that repeat exactly, as they are on Sqlite: the counter is
process-wide, and Npgsql's socket I/O completes on other threads, so a row can pick up background
allocation, and this capture's one launch per benchmark leaves that unaveraged. The integration
suite's `PostgresWorkloadAllocationGateTests` measures the same workloads with AllocationGate, which
waits for the steady state and reads the same bytes run after run:

| Workload | Hand-written ADO.NET | Hand-written `IAsyncDbConnection` | ZA.ORM |
|---|---:|---:|---:|
| Single-row read | 1,392 B | 1,600 B | 1,624 B |
| Insert, 3 parameters | 1,832 B | 2,008 B | 2,040 B |
| Multi-result read, as a batch | 3,720 B | 4,008 B | 4,056 B |

Use those figures for the gaps; the tables below for the comparison with Dapper.AOT. The
24 to 48 B between ZA.ORM and `HandWrittenAsyncDb` is its larger async state machine, boxed when the
call completes asynchronously; #427 and MarcelRoozekrans/AdoNet.Async#365 cover it.

Every query is a round trip to a server on the same machine, on a shared VM, and the RatioSD
column shows how far the timings spread: treat the time ratios as parity, not as a ranking.

## PostgresSingleRowReadBench

_Workload:_ `SELECT Id, CustomerId, Total FROM Orders WHERE Id = @id` against real Npgsql and `NUMERIC(18,4)`.

| Method             | Ratio | RatioSD | Allocated | Alloc Ratio |
|------------------- |------:|--------:|----------:|------------:|
| Dapper_AOT         |  0.78 |    0.15 |   1,968 B |        1.20 |
| ZeroAlloc_ORM      |  0.83 |    0.18 |   2,000 B |        1.22 |
| HandWrittenAsyncDb |  0.91 |    0.28 |   1,967 B |        1.20 |
| HandWrittenAdoNet  |  1.00 |         |   1,638 B |        1.00 |

## PostgresMultiRowReadBench

_Workload:_ 1000-row `SELECT … ORDER BY Id` drained into `List<OrderRow>`.

| Method            | Ratio | RatioSD | Allocated | Alloc Ratio |
|------------------ |------:|--------:|----------:|------------:|
| Dapper_AOT        |  0.87 |    0.27 |  58,436 B |        1.18 |
| ZeroAlloc_ORM     |  0.96 |    0.33 |  50,088 B |        1.01 |
| HandWrittenAdoNet |  1.00 |         |  49,589 B |        1.00 |

ZA.ORM allocates within 1% of hand-written ADO.NET, and Dapper.AOT 18% more.

## PostgresMultiResultSetBench

_Workload:_ head and 10 lines, Npgsql's multi-result-set path.

| Method                 | Ratio | RatioSD | Allocated | Alloc Ratio |
|----------------------- |------:|--------:|----------:|------------:|
| Dapper_AOT             |  0.87 |    0.20 |   3,335 B |        1.06 |
| ZeroAlloc_ORM          |  0.92 |    0.21 |   4,504 B |        1.43 |
| HandWrittenAsyncDb     |  0.92 |    0.21 |   4,448 B |        1.41 |
| HandWrittenAdoNet      |  1.00 |         |   3,151 B |        1.00 |
| HandWrittenNpgsqlBatch |  1.11 |    0.28 |   4,040 B |        1.28 |

`HandWrittenAdoNet` and Dapper.AOT run one `;`-joined command. ZA.ORM's `BatchMode.Auto` takes the
batch path, because Npgsql reports `CanCreateBatch`, so `HandWrittenNpgsqlBatch` is its fair
baseline: an `NpgsqlBatch` of the two statements costs about 900 B more than the joined command on
its own. `HandWrittenAsyncDb` runs the same batch over `IAsyncDbConnection`. Every hand-written row
grows an unsized `List<OrderLine>`, as ZA.ORM does. Whether `Auto` should prefer the joined command
on Npgsql is #427.

## PostgresInsertBench

_Workload:_ single-row INSERT returning rows affected.

| Method             | Ratio | RatioSD | Allocated | Alloc Ratio |
|------------------- |------:|--------:|----------:|------------:|
| Dapper_AOT         |  0.81 |    0.30 |   2,286 B |        1.05 |
| HandWrittenAsyncDb |  0.84 |    0.27 |   2,351 B |        1.08 |
| ZeroAlloc_ORM      |  0.88 |    0.31 |   2,120 B |        0.97 |
| HandWrittenAdoNet  |  1.00 |         |   2,176 B |        1.00 |

This table shows the background allocation at its worst: `HandWrittenAsyncDb` reads 231 B above
ZA.ORM, where the allocation gate measures it 32 B below.

## Takeaways

- **Time:** on a real round trip all rows are at parity within this capture's spread.
- **Allocation**, from the allocation gate:
  - ZA.ORM allocates 24 to 48 B per call more than the same code over `IAsyncDbConnection`.
  - Over hand-written ADO.NET, the gap is 232 B per read, 208 B per insert and 336 B per
    multi-result batch, most of it AdoNet.Async's.
  - ZA.ORM matches hand-written within 1% on the 1000-row read.
