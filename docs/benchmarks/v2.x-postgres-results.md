# v2.x Postgres benchmark results

**Status:** Captured 2026-10-21 at 2.4.0, from `main` at `129353d`.

> Allocations are exact. Speed is shown as same-run ratios; absolute timings are not published.

ZA.ORM is a **relative-position** tool: compare the rows of one table, never numbers across tables
or machines.

## Environment

```
BenchmarkDotNet v0.15.8, Windows 11 (10.0.26300.9711)
12th Gen Intel Core i9-12900HK 2.50GHz, 1 CPU, 20 logical and 14 physical cores
.NET SDK 10.0.402
  [Host] : .NET 10.0.13 (10.0.13, 10.0.1326.50504), X64 RyuJIT x86-64-v3
```

- An otherwise idle laptop. BenchmarkDotNet's default job ran out of process, with three launches
  per benchmark; the benchmark process was pinned to two performance cores with `--affinity 20`.
- Each launch boots its own Testcontainers `postgres:16-alpine` container through Docker 29.5.2 on
  the same machine, in a 4-CPU Docker VM that is not pinned.
- Packages: Npgsql 10.0.3, Testcontainers.PostgreSql 4.16.0, Dapper 2.1.89 and Dapper.AOT 1.1.0.

## Reproduction

```bash
# From repo root; Docker must be reachable.
dotnet run -c Release --project tests/ZeroAlloc.ORM.Benchmarks -- --filter "*Postgres*" --launchCount 3 --affinity 20
```

## How to read the tables

- **Ratio** is each row's mean time divided by `HandWrittenAdoNet`'s in the same run.
- **Launch range** is the same ratio computed from each launch's mean separately, to show how far
  it moved between processes.
- **Allocated** is bytes per operation from BenchmarkDotNet's GC counters.
- **Alloc Ratio** is each row's allocation divided by `HandWrittenAdoNet`'s.

Allocations are not whole numbers that repeat exactly, as they are on Sqlite: the counter is
process-wide, and Npgsql's socket I/O completes on other threads, so each launch picks up a few
bytes of background allocation.

Every query is a round trip to a server on the same machine. On this idle machine the launch
ranges stay within a few percent, unlike the earlier capture on a shared VM, where BenchmarkDotNet
reported a RatioSD around 0.3 for every row.

## PostgresSingleRowReadBench

_Workload:_ `SELECT Id, CustomerId, Total FROM Orders WHERE Id = @id` against real Npgsql and `NUMERIC(18,4)`.

| Method            | Ratio | Launch range | Allocated | Alloc Ratio |
|------------------ |------:|-------------:|----------:|------------:|
| HandWrittenAdoNet |  1.00 |              |   1,361 B |        1.00 |
| ZeroAlloc_ORM     |  1.03 |  1.01 – 1.08 |   1,690 B |        1.24 |
| Dapper_AOT        |  1.05 |  1.03 – 1.05 |   1,657 B |        1.22 |

## PostgresMultiRowReadBench

_Workload:_ 1000-row `SELECT … ORDER BY Id` drained into `List<OrderRow>`.

| Method            | Ratio | Launch range | Allocated | Alloc Ratio |
|------------------ |------:|-------------:|----------:|------------:|
| Dapper_AOT        |  0.99 |  0.98 – 0.99 |  58,056 B |        1.17 |
| HandWrittenAdoNet |  1.00 |              |  49,433 B |        1.00 |
| ZeroAlloc_ORM     |  1.01 |  1.01 – 1.02 |  50,201 B |        1.02 |

ZA.ORM allocates within 2% of hand-written ADO.NET, and Dapper.AOT 17% more. All three are at time
parity; the earlier capture's 12–29% gap for ZA.ORM came from the shared VM.

## PostgresMultiResultSetBench

_Workload:_ head and 10 lines through one `;`-joined batch, Npgsql's multi-result-set path.

| Method            | Ratio | Launch range | Allocated | Alloc Ratio |
|------------------ |------:|-------------:|----------:|------------:|
| Dapper_AOT        |  0.99 |  0.94 – 1.03 |   2,865 B |        1.07 |
| ZeroAlloc_ORM     |  1.00 |  0.94 – 1.05 |   4,194 B |        1.56 |
| HandWrittenAdoNet |  1.00 |              |   2,681 B |        1.00 |

ZA.ORM allocates about 1.5 KB more than hand-written ADO.NET here, the largest allocation gap in
either backend.

## PostgresInsertBench

_Workload:_ single-row INSERT returning rows affected.

| Method            | Ratio | Launch range | Allocated | Alloc Ratio |
|------------------ |------:|-------------:|----------:|------------:|
| Dapper_AOT        |  0.97 |  0.94 – 1.01 |   1,976 B |        1.01 |
| ZeroAlloc_ORM     |  0.98 |  0.98 – 0.99 |   2,105 B |        1.07 |
| HandWrittenAdoNet |  1.00 |              |   1,961 B |        1.00 |

## Takeaways

- **Time:** on a real round trip all three are at parity, within 5% on every workload.
- **Allocation:**
  - ZA.ORM matches hand-written within 2% on the multi-row read.
  - It allocates 7% more on inserts and 24% more on single-row reads.
  - It allocates 56% more on the multi-result-set batch.
