# v2.x Sqlite benchmark results

**Status:** Captured 2026-10-30 for [#351](https://github.com/ZeroAlloc-Net/ZeroAlloc.ORM/issues/351), on `main` at
`6b95bce` plus the per-dialect parameter names.

> Allocations are exact. Speed is shown as same-run ratios; absolute timings are not published.

ZA.ORM is a **relative-position** tool: compare the rows of one table, never numbers across tables
or machines.

## Environment

```
BenchmarkDotNet v0.15.8, Linux Debian GNU/Linux 13 (trixie)
Intel Core Ultra 7 255H 3.69GHz, 1 CPU, 12 logical and 12 physical cores
.NET SDK 10.0.403
  [Host] : .NET 10.0.14 (10.0.14, 10.0.1426.52326), X64 RyuJIT x86-64-v3
```

- A virtual machine shared with other workloads, not pinned. BenchmarkDotNet's default job ran
  out of process, with one launch per benchmark. The allocation figures do not depend on that;
  the time ratios do, so read them as rough, and see the RatioSD column.
- The benchmark project uses server GC with concurrent GC.
- Packages: Microsoft.Data.Sqlite 10.0.13, SQLitePCLRaw.lib.e_sqlite3 3.50.3, Dapper 2.1.89 and Dapper.AOT 1.1.0.

## Reproduction

```bash
# From repo root
dotnet run -c Release --project tests/ZeroAlloc.ORM.Benchmarks -- \
  --filter "ZeroAlloc.ORM.Benchmarks.SingleRowReadBench*" \
           "ZeroAlloc.ORM.Benchmarks.MultiRowReadBench*" \
           "ZeroAlloc.ORM.Benchmarks.MultiResultSetBench*" \
           "ZeroAlloc.ORM.Benchmarks.InsertBench*"
```

## How to read the tables

- **Ratio** is each row's mean time divided by `HandWrittenAdoNet`'s in the same run.
- **Allocated** is bytes per operation from BenchmarkDotNet's GC counters.
- **Alloc Ratio** is each row's allocation divided by `HandWrittenAdoNet`'s.
- `HandWrittenAdoNet` is written against `SqliteConnection` itself. `HandWrittenAsyncDb` is the
  same code against `IAsyncDbConnection`, the AdoNet.Async substrate ZA.ORM's generated code runs
  on. The gap between those two is AdoNet.Async's cost; the gap between `HandWrittenAsyncDb` and
  `ZeroAlloc_ORM` is the generator's.
- Every hand-written row binds `@id`, the name exactly as the SQL writes it, which
  Microsoft.Data.Sqlite resolves without retrying prefixes. ZA.ORM binds the same spelling since
  #351; see [Parameter prefixes](../cookbook/provider-quirks.md#parameter-prefixes).

## Before and after #351

ZA.ORM bound bare names such as `id` until #351. Microsoft.Data.Sqlite then retries `@`, `:` and `$`
in front of each name, building a string and a UTF-8 copy per try, on every statement. Both columns
were measured on this machine, before on `main` at `2d206ab`.

| Workload | Before | After | Saved |
|---|---:|---:|---:|
| `SingleRowReadBench`, 1 parameter | 1,568 B | 1,376 B | 192 B |
| `InsertBench`, 3 parameters | 1,856 B | 1,256 B | 600 B |
| `MultiResultSetBench`, 1 parameter in 2 statements | 3,400 B | 3,016 B | 384 B |

The integration suite's `SqliteWorkloadAllocationGateTests` holds each workload to these figures:
the generated method allocates exactly what `HandWrittenAsyncDb` does.

## SingleRowReadBench

_Workload:_ `SELECT Id, CustomerId, Total FROM Orders WHERE Id = @id`, 1 row materialised to `OrderRow`.

| Method             | Ratio | RatioSD | Allocated | Alloc Ratio |
|------------------- |------:|--------:|----------:|------------:|
| ZeroAlloc_ORM      |  0.84 |    0.27 |   1,376 B |        1.12 |
| HandWrittenAsyncDb |  0.87 |    0.29 |   1,376 B |        1.12 |
| Dapper_AOT         |  0.99 |    0.33 |   1,800 B |        1.46 |
| HandWrittenAdoNet  |  1.00 |         |   1,232 B |        1.00 |

ZA.ORM allocates what the same hand-written code over `IAsyncDbConnection` does. The 144 B over
hand-written ADO.NET are AdoNet.Async's. The baseline's RatioSD of 0.54 makes its time the least
reliable figure in the table.

## MultiRowReadBench

_Workload:_ 1000-row `SELECT … ORDER BY Id` drained into `List<OrderRow>`.

| Method            | Ratio | RatioSD | Allocated | Alloc Ratio |
|------------------ |------:|--------:|----------:|------------:|
| Dapper_AOT        |  0.94 |    0.02 | 130,000 B |        1.47 |
| HandWrittenAdoNet |  1.00 |         |  88,200 B |        1.00 |
| ZeroAlloc_ORM     |  1.05 |    0.04 |  88,592 B |        1.00 |

ZA.ORM is about 5% slower than hand-written ADO.NET and allocates 392 B more for 1000 rows, 0.4%.
Dapper.AOT is about 6% faster and allocates 47% more.

## MultiResultSetBench

_Workload:_ `SELECT head; SELECT lines`, the head and 10 lines as a `(Order, IReadOnlyList<OrderLine>)` tuple.

| Method             | Ratio | RatioSD | Allocated | Alloc Ratio |
|------------------- |------:|--------:|----------:|------------:|
| HandWrittenAdoNet  |  1.00 |         |   2,872 B |        1.00 |
| ZeroAlloc_ORM      |  1.01 |    0.03 |   3,016 B |        1.05 |
| HandWrittenAsyncDb |  1.02 |    0.04 |   3,016 B |        1.05 |
| Dapper_AOT         |  1.26 |    0.04 |   4,264 B |        1.48 |

Microsoft.Data.Sqlite has no batch support, so every row runs one `;`-joined command. The
hand-written rows now grow an unsized `List<OrderLine>`, as ZA.ORM's generated code does: neither
knows the line count in advance. Earlier captures sized it to the ten lines, which saved the
baseline 192 B ZA.ORM could not save. ZA.ORM allocates what `HandWrittenAsyncDb` does.

## InsertBench

_Workload:_ `INSERT INTO Orders (Id, CustomerId, Total) VALUES (@id, @cust, @total)` returning rows affected.

| Method             | Ratio | RatioSD | Allocated | Alloc Ratio |
|------------------- |------:|--------:|----------:|------------:|
| ZeroAlloc_ORM      |  0.93 |    0.05 |   1,256 B |        1.04 |
| HandWrittenAdoNet  |  1.00 |         |   1,208 B |        1.00 |
| HandWrittenAsyncDb |  1.08 |    0.09 |   1,256 B |        1.04 |
| Dapper_AOT         |  1.24 |    0.11 |   1,888 B |        1.56 |

ZA.ORM allocates 48 B more than hand-written ADO.NET, all of it AdoNet.Async's, down from 648 B.
Dapper.AOT allocates the most.

## Takeaways

- **Allocation:** on every single-statement workload ZA.ORM allocates exactly what hand-written
  code over `IAsyncDbConnection` does. What remains over hand-written ADO.NET is AdoNet.Async's:
  144 B per read, 48 B per insert and 144 B per multi-result read. MarcelRoozekrans/AdoNet.Async#365
  works on it.
- **Multi-row reads (1000 rows):** ZA.ORM allocates 0.4% more than hand-written ADO.NET.
  Dapper.AOT is faster but allocates 47% more.
- **Time:** ZA.ORM is within a few percent of hand-written ADO.NET on every workload, and ahead
  of Dapper.AOT on all but the 1000-row read. This capture's VM was shared, so treat the time
  ratios as rough.
