# v2.x Sqlite benchmark results

**Status:** Captured 2026-10-21 at 2.4.0, from `main` at `129353d`.

> Allocations are exact. Speed is shown as same-run ratios; absolute timings are not published.

ZA.ORM is a **relative-position** tool: compare the rows of one table, never numbers across tables
or machines.

## Environment

```
BenchmarkDotNet v0.15.8, Windows 11 (10.0.26300.9711)
12th Gen Intel Core i9-12900HK 2.50GHz, 1 CPU, 20 logical and 14 physical cores
.NET SDK 10.0.402
  [Host] : .NET 10.0.13 (10.0.13, 10.0.1326.50504), X64 RyuJIT x86-64-v3
```

- An otherwise idle laptop. BenchmarkDotNet's default job ran out of process, with three launches
  per benchmark, pinned to two performance cores with `--affinity 20`.
- The benchmark project uses server GC with concurrent GC.
- Packages: Microsoft.Data.Sqlite 10.0.13, SQLitePCLRaw.lib.e_sqlite3 3.50.3, Dapper 2.1.89 and Dapper.AOT 1.1.0.

## Reproduction

```bash
# From repo root
dotnet run -c Release --project tests/ZeroAlloc.ORM.Benchmarks -- \
  --filter "ZeroAlloc.ORM.Benchmarks.SingleRowReadBench*" \
           "ZeroAlloc.ORM.Benchmarks.MultiRowReadBench*" \
           "ZeroAlloc.ORM.Benchmarks.MultiResultSetBench*" \
           "ZeroAlloc.ORM.Benchmarks.InsertBench*" \
  --launchCount 3 --affinity 20
```

## How to read the tables

- **Ratio** is each row's mean time divided by `HandWrittenAdoNet`'s in the same run.
- **Launch range** is the same ratio computed from each launch's mean separately, to show how far
  it moved between processes.
- **Allocated** is bytes per operation from BenchmarkDotNet's GC counters.
- **Alloc Ratio** is each row's allocation divided by `HandWrittenAdoNet`'s.

BenchmarkDotNet's allocation figure was cross-checked against each row's Gen0 collection count.
One row disagreed: BenchmarkDotNet reported 27,721 B for ZA.ORM's single-row read, with the same
number of collections as its neighbours. A per-thread measurement with
`GC.GetAllocatedBytesForCurrentThread()` over 20,000 reads, the method `AllocationGate` uses, gave
1,568 B, the same figure as the 2.3.1 capture, and the table shows that.

## SingleRowReadBench

_Workload:_ `SELECT Id, CustomerId, Total FROM Orders WHERE Id = @id`, 1 row materialised to `OrderRow`.

| Method            | Ratio | Launch range | Allocated | Alloc Ratio |
|------------------ |------:|-------------:|----------:|------------:|
| HandWrittenAdoNet |  1.00 |              |   1,232 B |        1.00 |
| ZeroAlloc_ORM     |  1.06 |  1.05 – 1.07 |   1,568 B |        1.27 |
| Dapper_AOT        |  1.21 |  1.21 – 1.22 |   1,800 B |        1.46 |

ZA.ORM is about 6% slower than hand-written ADO.NET and allocates 336 B more per read. Dapper.AOT
is about 21% slower and allocates 568 B more.

## MultiRowReadBench

_Workload:_ 1000-row `SELECT … ORDER BY Id` drained into `List<OrderRow>`.

| Method            | Ratio | Launch range | Allocated | Alloc Ratio |
|------------------ |------:|-------------:|----------:|------------:|
| Dapper_AOT        |  0.94 |  0.93 – 0.94 | 130,001 B |        1.47 |
| HandWrittenAdoNet |  1.00 |              |  88,200 B |        1.00 |
| ZeroAlloc_ORM     |  1.06 |  1.05 – 1.07 |  88,592 B |        1.00 |

ZA.ORM is about 6% slower than hand-written ADO.NET and allocates 392 B more for 1000 rows, 0.4%.
Dapper.AOT is about 6% faster and allocates 47% more.

## MultiResultSetBench

_Workload:_ `SELECT head; SELECT lines`, the head and 10 lines as a `(Order, IReadOnlyList<OrderLine>)` tuple.

| Method            | Ratio | Launch range | Allocated | Alloc Ratio |
|------------------ |------:|-------------:|----------:|------------:|
| HandWrittenAdoNet |  1.00 |              |   2,680 B |        1.00 |
| ZeroAlloc_ORM     |  1.09 |  1.09 – 1.10 |   3,400 B |        1.27 |
| Dapper_AOT        |  1.27 |  1.26 – 1.27 |   4,072 B |        1.52 |

ZA.ORM is within 10% of hand-written ADO.NET; at v0.7.0 it was 30% slower. Dapper.AOT is 27% slower
and allocates the most.

## InsertBench

_Workload:_ `INSERT INTO Orders (Id, CustomerId, Total) VALUES (@id, @cust, @total)` returning rows affected.

| Method            | Ratio | Launch range | Allocated | Alloc Ratio |
|------------------ |------:|-------------:|----------:|------------:|
| HandWrittenAdoNet |  1.00 |              |   1,208 B |        1.00 |
| Dapper_AOT        |  1.17 |  1.15 – 1.18 |   1,888 B |        1.56 |
| ZeroAlloc_ORM     |  1.20 |  1.16 – 1.26 |   1,856 B |        1.54 |

ZA.ORM is about 20% slower than hand-written ADO.NET and allocates 648 B more per insert. At v0.7.0
it allocated 4% more than hand-written; that gap has grown. Dapper.AOT takes about the same time and
allocates about the same.

## Takeaways

- **Multi-row reads (1000 rows):** ZA.ORM is 6% slower than hand-written ADO.NET and allocates 0.4% more. Dapper.AOT is 6% faster but allocates 47% more.
- **Multi-result-set:** ZA.ORM is within 10% of hand-written, down from 30% at v0.7.0, and ahead of Dapper.AOT.
- **Single-row reads:** ZA.ORM sits between hand-written ADO.NET and Dapper.AOT on both time and allocation.
- **Inserts:** ZA.ORM and Dapper.AOT are level, about 20% slower than hand-written.
- **Allocation:** ZA.ORM allocates more than hand-written on every single-statement workload: 336 B per read and 648 B per insert.
